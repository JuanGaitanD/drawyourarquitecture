# Revisión técnica independiente del stack

## Veredicto

Se mantiene la mayor parte del stack, con condiciones: es adecuado para un MVP personal, no para reproducir el inventario completo de Miro en seis horas.  
SPA sí para dashboard y editores; una capa HTML pública es opcional y solo necesaria si se exigen metadatos o previews específicos por proyecto.  
Vite sí; para un proyecto nuevo recomiendo Vite 8.3.x, React 19 y TypeScript strict, fijados tras comprobar los dos motores; Vite 7.3.x sigue siendo una alternativa soportada.  
Mantener Excalidraw para notas y React Flow para un board deliberadamente reducido, con implementaciones propias de las funciones que no incluye.  
Mantener Firebase y Vercel Pro; reemplazar la promesa de «tiempo real listo» por un plan explícito de concurrencia y migración.  
Posponer ELK y colaboración; limitar Zustand/zundo al board, conservar el historial nativo de Excalidraw y añadir primitivas accesibles.  
Usar un paquete único con límites entre módulos, formatos versionados y puertos pequeños; no crear un monorepo ni un motor universal.

Fecha de consulta: **2026-11-05**. Revisión documental; no se instaló ni ejecutó la app. **Verificado** significa documentación o metadatos publicados consultados; **inferencia** significa recomendación técnica; **no verificado** indica que falta evidencia o una prueba ejecutable.

Se leyeron en orden `docs/stack.md`, `docs/research/excalidraw.md` y `docs/research/miro.md`. Ambos inventarios existían y tenían secciones de cierre y limitaciones; no parecían documentos a medio escribir y no fue necesario esperar. Son evidencia secundaria: Miro no se pudo operar autenticado y parte de sus comportamientos/atajos son inferidos; la receta de embeds de Excalidraw tampoco fue ejecutada.

## SPA, metadatos públicos y alternativas

**Decisión para este caso: SPA ahora, con posibilidad de una ruta pública híbrida.** Ni dashboard autenticado ni `/embed/board/:id` requieren SEO. El enlace público tampoco implica automáticamente que el contenido deba indexarse. Recomiendo `noindex` por defecto para proyectos personales compartidos; publicar no equivale a consentir indexación.

| Enfoque | Aplicación concreta | Balance en seis horas |
|---|---|---|
| Vite SPA | Editores lazy, dashboard y viewer en cliente; metadatos generales en HTML inicial. | Menor complejidad operativa; suficiente si se acepta una tarjeta de enlace genérica. Es mi elección. |
| Next.js mixto | HTML y metadatos del proyecto en servidor; wrapper de Excalidraw solo cliente, board interactivo en cliente. | Válido, no incompatible con canvas. Preferible desde el inicio si OG individual, páginas indexables o lógica servidor amplia son requisitos obligatorios. Añade fronteras servidor/cliente y autenticación servidor que aquí no son necesarias todavía. |
| React Router framework mode | CSR, SSR y prerender; editores dentro de una frontera cliente. Es la alternativa actual a evaluar para el enfoque de framework de Remix. | Buen paso si crecen loaders/actions y rutas públicas. Para cinco rutas sin servidor no aporta suficiente frente a wouter. [Estrategias oficiales](https://reactrouter.com/start/framework/rendering). |
| TanStack Start | Router tipado, SSR selectivo y modo SPA con shell prerenderizado. | Capaz; el shell prerenderizado no genera por sí solo metadata para cada proyecto dinámico. Más convenciones que aprender sin una necesidad actual. [Modo SPA](https://tanstack.com/start/latest/docs/framework/react/guide/spa-mode). |
| Vite + HTML público pequeño | Una función para `/view/:type/:id` comprueba publicación y devuelve shell con título, descripción y miniatura; el editor sigue en cliente. | Mejor ampliación si solo hacen falta previews personalizados. Es trabajo adicional real, no «activar un rewrite». Añadirlo después si se acepta OG genérico inicialmente. |

Open Graph se expresa en metadatos HTML, incluyendo título, tipo, URL e imagen ([protocolo](https://ogp.me/)). Inferencia de diseño: entregar esos tags en la respuesta inicial evita depender de que cada consumidor ejecute JS; no se verificó el comportamiento de WhatsApp, Slack u otras plataformas concretas. Una miniatura puede producirse al publicar desde el cliente y almacenarse; no hace falta ejecutar canvas en servidor.

Si se implementa HTML público, comprobar `isPublic` en **cada lectura autorizada**, escapar títulos y no usar una URL arbitraria del usuario como destino de fetch. Un SDK Admin omite reglas: la función debe comprobar permisos explícitamente. Invalidar caché al despublicar; no cachear HTML privado ni responder metadatos privados a bots. Prerender en build solo sirve para páginas conocidas que se regeneran; no resuelve proyectos cambiantes sin política de actualización. **Edge no es requisito**: elegir runtime por SDK y autorización disponibles, no por el nombre del hosting.

## Compatibilidad efectiva y problemas de integración

### Versiones observadas, sin presentar un lockfile ficticio

Se consultaron por HTTP público los endpoints npm `/latest` y el manifiesto publicado de Excalidraw; no se ejecutó npm ni un CLI de cuenta. Resultado: React 19.3.1; Vite 8.3.6; TypeScript 7.0.2; Excalidraw 0.18.1; React Flow 12.12.1; wouter 3.13.0; elkjs 0.12.1; Dagre 3.1.3; Zustand 5.0.16; zundo 2.3.0; Firebase 13.2.0; Vitest 5.1.0; Playwright 1.64.1. Son observaciones fechadas, no obligación de adoptar todo `latest` simultáneamente.

Vite actual exige Node `^20.19.0 || >=22.12.0`, mientras Vitest 5 exige `^22.12.0 || ^24.0.0 || >=26.0.0`: propongo Node 24 y fijar el patch al implementar. `@vitejs/plugin-react` 6.2.1 declara Vite `^8.0.0`; no combinarlo por accidente con Vite 7. Para conservar Vite 7, el [plugin React 5.0.4](https://registry.npmjs.org/@vitejs%2Fplugin-react/5.0.4) declara compatibilidad con esa rama; revisar su patch adecuado al crear el lockfile. Vitest 5 acepta Vite 6.4/7/8. Fuentes: [plugin React actual](https://registry.npmjs.org/@vitejs%2Fplugin-react/latest), [Vite](https://registry.npmjs.org/vite/latest), [Vitest](https://registry.npmjs.org/vitest/latest). No se comprobó compilación con TS 7 ni todos los plugins/transitivos; si hay incompatibilidad, fijar una versión estable verificada sin cambiar de arquitectura.

**Excalidraw + React 19: confirmado a nivel de peers. Excalidraw + Vite 7.3/8.3: viable por formato ESM, sin peer de Vite, pero ejecución conjunta NO VERIFICADA.** El soporte de React 19 tuvo una incidencia histórica [#8923, cerrada por #9182](https://github.com/excalidraw/excalidraw/issues/8923); no es evidencia de incompatibilidad actual. Antes de comprometer el stack, la implementación debe comprobar dev y build/preview de producción con las versiones fijadas, nota con texto/imagen, exportación y board embebido. Esta revisión no instala dependencias por instrucción del encargo.

- **CSS/altura:** import obligatorio `@excalidraw/excalidraw/index.css`, CSS de React Flow y contenedor con dimensiones. El problema de CSS en Next 15 [#9156](https://github.com/excalidraw/excalidraw/issues/9156) está cerrado; no extrapolarlo a Vite actual ni parchear `node_modules` preventivamente.
- **Fuentes:** por defecto Excalidraw usa CDN; si se autoalojan, copiar sus fuentes y definir `EXCALIDRAW_ASSET_PATH` antes del montaje. Verificar texto y export tras la carga, también con red lenta. [Instalación oficial](https://docs.excalidraw.com/docs/@excalidraw/excalidraw/installation).
- **Peso:** dos motores no deben entrar en el dashboard inicial. Import dinámico por ruta y montaje diferido de embeds; dejar que el bundler fragmente antes de imponer `manualChunks`. Los tamaños del inventario no se midieron independientemente; bytes descomprimidos del paquete no equivalen a transferencia inicial comprimida. **Bundle y rendimiento reales no verificados.**
- **SSR:** Excalidraw debe quedar fuera de la evaluación en servidor, incluyendo imports auxiliares de su wrapper. La documentación propone import dinámico sin SSR ([integración](https://docs.excalidraw.com/docs/@excalidraw/excalidraw/integration)). Esto permite un shell Next sin convertir el editor en renderizable en servidor.
- **Embeds:** `validateEmbeddable` admite función; `undefined` vuelve al validador integrado ([props](https://docs.excalidraw.com/docs/@excalidraw/excalidraw/api/props/)). Para permitir exclusivamente boards propios, devolver boolean explícito tras validar origen, protocolo y ruta. No usar `true` global ni regex solo de hostname. `renderEmbeddable` permite sustituir el iframe por React ([render props](https://docs.excalidraw.com/docs/@excalidraw/excalidraw/api/props/render-props)).
- **Hallazgo en investigación local:** su §3 propone `BoardEmbed = segundo Excalidraw`, incompatible conceptualmente con boards React Flow. Debe ser un `BoardViewer` de React Flow o una miniatura, nunca reinterpretar nodos/aristas como escena Excalidraw. El fallback `null` a iframe y sus detalles de sandbox proceden del análisis secundario; **no se revalidaron aquí en ejecución ni en el bundle**.
- **Advertencia documental:** FAQ/integración aún muestran referencias a UMD y `process.env.IS_PREACT`, mientras el paquete 0.18.1 exporta ESM condicional. No copiar un define `IS_PREACT=true` en una app React. Si aparece `process is not defined`, aislar la referencia concreta del artefacto elegido; no añadir un polyfill global a ciegas.

## Cobertura del inventario de Miro

React Flow cubre la base de grafo: viewport, selección, arrastre, handles, edges, controles, minimapa, grid y resize. La documentación de [ejemplos](https://reactflow.dev/examples) distingue funciones de librería, recetas MIT y ejemplos Pro. Que exista un ejemplo no significa que venga implementado en el paquete.

| Inventario | Cobertura y trabajo pendiente | Recomendación v1 |
|---|---|---|
| Formas, texto, stickies, iconos | Nodos propios con edición de texto, estilos persistentes y geometría de handles; catálogo cloud requiere assets/licencias. | Rectángulo, rombo, texto y sticky; pocos iconos genéricos. No prometer las 39 formas. |
| Conectores | Edges y etiquetas soportados. Extremos libres, múltiples captions, puntos editables y evitar obstáculos necesitan extensión. Smooth-step no equivale a routing Miro. | Extremos enlazados, etiqueta única y flechas; declarar fuera extremos libres y routing avanzado. |
| Frames y grupos | `parentId`/subflows dan jerarquía. Reparenting, coordenadas relativas, selección agrupada y mover/redimensionar frame son lógica adicional. | Frame básico solo si pasa mover/guardar/recargar; diferir agrupación arbitraria. |
| Alinear/distribuir, formato, Z | Requieren comandos de producto y UI; estilos de nodos/edges permiten representarlos. | Alinear simple y controles de relleno/borde/texto; sin capas avanzadas. |
| Undo, clipboard, export PNG/SVG | No son un conjunto acabado de serie. Export DOM/SVG con fuentes, imágenes y CORS necesita validación propia. | Undo por gesto, duplicar y backup JSON; PNG si queda validado. No prometer SVG fiel como parte «gratis» del motor. |
| Mind map, Mermaid bidireccional, tablas, comentarios, IA, plantillas | Producto adicional sobre el motor; la sincronización texto↔grafo es especialmente costosa. | Posponer. Un inventario competitivo no es un contrato de MVP. |

Si **todo lo marcado P0 por Miro** es obligatorio, React Flow más nodos propios deja de ser una opción demostrablemente óptima para seis horas: faltan demasiados comportamientos. Recomiendo renegociar alcance antes que añadir Konva o un tercer motor. tldraw podría reducir desarrollo de whiteboard, pero su licencia de producción discrecional y las obligaciones de los forks perjudican este proyecto personal open source; no depende solo de pagar o mostrar una marca.

## Repositorio propuesto

Un `package.json`, un lockfile y un build. Árbol conceptual: crear carpetas cuando tengan su primer archivo, no scaffolding vacío.

```text
src/
  app/                         # rutas, shell, composición e inyección de adaptadores
  domain/                      # identidad/tipo de proyecto, publicación, referencias, invariantes
  application/                 # cargar/guardar/publicar y contratos de repositorio/archivos/identidad
  infrastructure/firebase/     # SDK, reglas de conversión, adapters Auth/Firestore/Storage
  editors/
    note/                      # wrapper Excalidraw, codec versionado y puente de embeds
    board/                     # modelo/comandos puros, codec, store por instancia y UI React Flow
  ui/                          # primitivas compartidas, tokens, temas y estados comunes
tests/
  rules/                       # permisos reales contra emuladores
  e2e/                         # recorridos entre rutas, publicación y persistencia
docs/                          # decisiones e investigación existentes
```

Pruebas unitarias junto al módulo probado. Reglas Firestore/Storage, índices y configuración de despliegue junto a la configuración raíz que consume cada herramienta. `public/` solo para assets realmente autoalojados. Una eventual función de HTML público en `api/` pertenece al mismo paquete mientras comparta despliegue.

**Regla de dependencia:** `application → domain`; `infrastructure → application/domain`; UI y adaptadores de motores consumen casos de uso/contratos; `app` conoce las implementaciones y las conecta. Dominio y aplicación no importan React, Firebase, Zustand, Excalidraw ni React Flow. En board, React Flow depende del modelo/comandos propios, no al revés. Aplicar con restricciones ESLint de imports y revisión, sin framework de inyección.

Los límites no requieren una clase por verbo. Puertos pequeños: repositorio de proyectos/documentos, almacenamiento de archivos e identidad. Devolver IDs, revisiones y datos propios, no `DocumentSnapshot`, referencias Firebase ni usuarios SDK. El dominio compartido conoce un sobre `{id, kind, schemaVersion, revision, payload}`; cada motor valida/migra su payload. Puede conservarse el formato nativo versionado de Excalidraw en su adaptador: **no** reescribir todas sus entidades para aparentar independencia. Cambiar de backend será mucho más fácil que cambiar de motor; no prometer sustitución gratuita de ambos.

Para incrustar, la nota emite una referencia estable `boardId` (codificada en URL o metadata del elemento) y solicita una función de renderizado que `app` inyecta. Esa función monta `BoardViewer` sin herramientas de edición, con datos cargados por el mismo caso de uso autorizado. Note no importa implementación ni store de board; comparte solo el contrato de referencia y render. Store/Provider independiente por viewer; no listeners globales de teclado. Preferir miniatura y activación explícita para varios embeds. La ruta `/embed/board/:id` reutiliza el viewer, no se exige un iframe interno.

Un board privado incrustado en una nota pública **continúa privado**; placeholder sin acceso. No publicar descendientes automáticamente ni resolverlos con credenciales del propietario en servidor. En v1 permitir solo nota→board, sin embeds dentro de board: elimina ciclos. Si se amplía después, añadir límite de profundidad y conjunto de IDs visitados. Exportar una nota con embeds exige una política explícita de miniaturas/fallback; no asumir que el DOM de un board aparecerá dentro del PNG Excalidraw.

**No crear todavía:** workspaces `apps/*`/`packages/*`, paquete de design system, backend propio, bus de eventos, CQRS, repositorio genérico CRUD, registro universal de plugins/motores, paquetes de colaboración ni layout, ni servicios por cada nodo. Extraer un paquete solo con segundo consumidor o ciclo de release independiente. Esto mantiene responsabilidad única e inversión de dependencias sin convertir SOLID en infraestructura anticipada.

## Persistencia y camino a colaboración

1. Metadatos separados de escena: dueño, tipo, título, publicación y revisión no deben viajar con cada movimiento. Payload versionado sin estado de selección/cursor. Para escenas pequeñas puede ser JSON serializado bajo un límite conservador; al superar el límite, blob inmutable en Storage y puntero. Umbral propuesto inicial: 700 KiB medidos en UTF-8; **heurística, no límite oficial ni tamaño validado**.
2. Guardado serializado por proyecto, debounce y estado visible «guardando/guardado/error». Revision esperada en transacción para detectar otra pestaña: detener sobrescritura y ofrecer recargar/guardar copia. Un solo dueño también puede editar desde dos dispositivos. `pagehide` no garantiza terminar escrituras de red: no confiar solo en el flush final. Copia local de recuperación sin service worker es un buen siguiente paso.
3. Con blobs, subir primero la versión nueva y después cambiar el puntero mediante la revisión; si falla, conservar la anterior. Barrido de huérfanos puede esperar; integridad de referencias no. Excluir payload de índices que no se consultan.
4. Lecturas públicas por ID y proyecto publicado; lista del dashboard limitada al dueño. Reglas validan dueño inmutable, campos permitidos, tipo y revisión; Storage debe aplicar permisos equivalentes. Pruebas contra usuario ajeno y sin sesión son parte del MVP. [Reglas y SDK servidor](https://firebase.google.com/docs/firestore/security/rules-conditions).
5. Fase 2: para board, tipos compartidos por ID/campo con Yjs y provider, o almacenamiento colaborativo Liveblocks. Presencia fuera del documento persistente; undo local por origen. Mantener invariantes de aristas y borrados: un CRDT converge, pero no garantiza un grafo de producto válido. Para notas, adaptar las APIs de reconciliación de Excalidraw; no insertar un JSON gigante en un registro CRDT y llamarlo colaboración. **Integración exacta de ambos motores no verificada.**

Supabase es una alternativa fuerte si se necesitan SQL, relaciones y portabilidad del servidor; su Broadcast podría transportar operaciones, pero requiere definir recuperación y persistencia. Postgres propio da control a cambio de API, permisos, despliegue y operación. Con la preferencia previa por Firebase, cambiar ahora aumentaría aprendizaje sin resolver las partes difíciles de edición concurrente. Liveblocks probablemente reduce operación del tiempo real, a cambio de servicio externo y coste; **no se compararon precios ni cuotas de una carga real**.

## Decisiones técnicas para una UI cuidada

El stack lo permite; no lo garantiza. Definir desde el inicio tokens semánticos de superficie, texto, borde, selección, foco, peligro, radios, espaciado, sombra y z-index. Una fuente de verdad para tema `light/dark/system`, con adaptación al prop/theme de cada motor y `color-scheme` del documento. Diferenciar colores de interfaz y colores persistidos del dibujo: cambiar tema no debe reescribir los colores de los nodos.

Radix es mi elección para overlays y menús con CSS Modules; React Aria sería buena alternativa si su equipo ya lo conoce. Mantener etiquetas accesibles, retorno de foco y navegación de teclado de las primitivas; las etiquetas y el orden de tabulación siguen siendo responsabilidad de la app. Atajos limitados al editor enfocado, ignorando inputs y composición IME, con Escape y sin competir entre la nota y su embed. [React Flow ofrece foco/teclado y textos ARIA configurables](https://reactflow.dev/learn/advanced-use/accessibility); no desactivarlos globalmente para arreglar un conflicto local.

Elegir una tipografía de UI y escala antes de pulir componentes; una pila de sistema inicialmente evita descargas. Si se incorpora una fuente, fijar licencia y alojamiento. No intentar sustituir las fuentes de dibujo con la fuente del shell. Iconos con tamaño y grosor consistentes, botones con nombre accesible y tooltips que no sean su única etiqueta. Prever portal root y z-index para que menús no queden recortados por el lienzo.

Para lienzos grandes: nodos y handlers estables, selectores estrechos y no suscribirse al grafo entero para pintar la barra; simplificar contenido a zoom bajo y diferir imágenes/embeds. [Guía de rendimiento de React Flow](https://reactflow.dev/learn/advanced-use/performance). No serializar ni escribir Firestore en cada frame. Si luego se añade ELK, ejecutar layout en worker y aplicar un único comando al terminar. Ningún número máximo de nodos/FPS fue verificado en este repositorio: medir con un documento representativo antes de prometer capacidad.

La evaluación de principios de UI usó [Web Interface Guidelines](https://raw.githubusercontent.com/vercel-labs/web-interface-guidelines/main/command.md): foco visible, nombres de controles, estados de interacción, carga/errores y tema. No hay UI implementada que permita emitir un dictamen WCAG. El mínimo de 1024 px no elimina la necesidad de probar zoom del navegador, textos largos y paneles que reduzcan el área útil.

## Riesgos y recortes

| Prioridad | Riesgo | Respuesta y recorte |
|---|---|---|
| Crítico | Confundir inventario de Miro con alcance de seis horas | Acordar board mínimo: crear nodos, texto editable, conectar, mover, borrar, undo, guardar y lectura pública. El resto va a backlog, aunque el inventario lo llame P0. |
| Crítico | Fuga de datos por compartir o por embeds | Reglas antes del enlace público, prueba sin sesión, prohibición de escritura ajena y de publicar hijos privados. No recortar seguridad para conservar herramientas. |
| Alto | Pérdida de trabajo por debounce o dos pestañas | Guardado con revisión y errores visibles, recarga comprobada y backup JSON. No fiarse solo del cierre de pestaña. |
| Alto | Integración dual de motores/export/embeds consume el plazo | Primero validar la pareja React/Vite/Excalidraw y el board mínimo. Si el embed interactivo falla, miniatura enlazada con referencia estable; conservar posibilidad de mejora. |
| Alto | Fase 2 subestimada como activar listeners | Separar estado UI/documento y versionar formatos hoy; posponer proveedor y binding. Presupuestar colaboración como fase propia con pruebas de concurrencia y reconexión. |
| Medio | Licencias y dependencias condicionan forks | Mantener avisos MIT/Unlicense/ISC aplicables; ELK y tldraw requieren tratamiento distinto. Evitar ejemplos Pro y assets cloud no revisados. |
| Medio | Coste operativo inesperado | Blaze explícito, límites de archivos/escenas y control de frecuencia de guardado. No calcular costes con tamaños/FPS supuestos. |

**Orden de recorte:** IA, tablas, comentarios, presentaciones, importaciones y Mermaid bidireccional; después mind map/ELK, guías inteligentes, catálogo cloud amplio y agrupación avanzada; después SVG/PNG sofisticado y embed vivo, sustituyéndolos por backup JSON/miniatura. Diferir metadatos OG individuales si se acepta tarjeta genérica. Conservar los dos tipos de proyecto, persistencia fiable, dueño único, lectura pública autorizada y coherencia básica de tema/foco. No existe evidencia para prometer el producto completo y pulido en seis horas; estas seis horas deben tratarse como MVP limitado.

## Límites de esta revisión

- No se ejecutaron build, SSR, export, reglas ni flujos de interacción: es una revisión previa al código.
- Versiones y peers fueron leídos del registro en la fecha indicada; no prueban compatibilidad de todas las dependencias transitivas ni sustituyen lockfile.

- El detalle completo de obligaciones legales transitivas, términos de assets cloud, costes por tráfico y compatibilidad exacta Yjs/Excalidraw/React Flow requiere comprobación al seleccionar versiones y alcance. No se asume que open source implique producción gratuita de todos los servicios.
